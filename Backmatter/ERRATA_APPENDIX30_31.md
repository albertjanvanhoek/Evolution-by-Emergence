# Errata to Appendices 30 and 31 ("Existence First")

`Appendix30.tex` and `Appendix31.tex` are lineage. They are kept as written (working agreement 6 in [CLAUDE.md](../CLAUDE.md)) and are not part of the checked core. Several of their mathematical statements do not hold as written. This note lists them so that no reader takes them as proved. The author asked for this note, in D16 of [DIALOGUE.md](../DIALOGUE.md).

The counterexamples come from research report 1 on the existence conjecture ([research/existence/sources/REPORT_1_EXISTENCE.md](../research/existence/sources/REPORT_1_EXISTENCE.md)). The assistant checked each one against the text of the appendices on 10 October 2026. They are counterexamples to the appendices, not to the current Lean modules.

| Where | What the appendix says | Why it fails | What a repair needs |
|---|---|---|---|
| Appendix 30, remark after Definition `def:kcover`; Appendix 31, `def:kcover` | Coverage implies `L ≤ k_min`: at least as many monitors as substrates. | Coverage only says each substrate has *some* sensitive monitor. One monitor can be sensitive to several substrates. With two substrates and one monitor `O(x₁, x₂) = x₁ + x₂`, both partial derivatives are nonzero, so `k_min = 1 < L = 2`. Being sensitive to a substrate is also not the same as being able to certify it. | Define coverage as valid certification of each constraint, or add the assumption of one distinct monitor per substrate explicitly. |
| Appendix 31, Definition `def:barrier_monitor` | The observed barrier satisfies `inf h(x') ≥ h(x) − L·ε` over states `x'` compatible with the observation. | A Lipschitz constant in the state does not bound how much `h` varies along a direction the monitor cannot see. Take `O(x) = x₁`, `h(x) = x₂`, the true state `x = (0, 1)`, no observation error, and the state space `[0,1] × [−1,1]`. The compatible states have `x₁ = 0` and any `x₂`, so the infimum is `−1`, while `h(x) − L·0 = 1`. | Add a justified bound on how `h` varies within the states that look the same to the monitor. The weaker statement, that a nonnegative infimum implies the true state is safe, still holds. |
| Appendix 30, Theorem `thm:forward_inv`; Appendix 31, execution rule H1 | Forward invariance: the safe set is kept at every step. The proof says a certified action "exists and is executed". | The execution rule checks whether monitors approve the *current state*. It does not check the *action* that is executed. At the safe state `x = 1` with `x' = x + a`, the safe action `a = 0` exists, but executing `a = −2` gives `x' = −1`. Approval of the state does not prevent this. | Require the executed action itself to carry a next-state certificate, and specify a safe fallback when approval is absent. |
| Appendix 30, "Constructive sufficient condition" (equation `eq:sufficient`); the same idea in Appendix 31 | If `L⁽ᵃ⁾·Δa_max` exceeds the disturbance and floor terms, a one-step certificate applies. | A Lipschitz constant is an upper bound on how much an action *can* change a barrier. It does not guarantee that some action changes it in the helpful direction. Several barriers may also need incompatible actions. | Show a reachable helpful change, and one action that satisfies all barriers at once against the declared disturbances. |
| Appendix 30, Theorem `thm:ratchet`; Appendix 31, kernel hypothesis H2 | If the new kernel is nonempty and lies inside the old one, a safe controller exists after the floor rises. | Nonempty and nested does not mean the *present* state is in the new kernel. With `x' = x`, old kernel `[0, 2]`, new kernel `[1, 2]` and the present state `0`, the state cannot reach the new kernel, so no safe controller exists after the floor rises. | Certify that the present state lies in the new kernel, or that a feasible transition into it exists, before raising the floor. |
| Appendix 31, Theorem `thm:capture`; Appendix 30, emergence theorem, part B | Capturing the system costs at least `k_min · min C_FN`. | Only the monitors that cover the *violated* constraint have to give false approvals. Take two monitors, each covering one substrate, so `k_min = 2`, with a false approval costing 1 each. If only the first substrate fails, the second monitor approves honestly, and capturing the first alone costs 1, below the stated bound of 2. | Count the false approvals needed for the particular constraints that are violated, not the size of the cover. |

## Reported, not yet checked

- **The multiplicative viability index (Appendix 30)** does not become zero when one substrate falls below a positive floor: a ratio of `0.5/1` is still positive. Appendix 31 treats the index more cautiously, as a heuristic. The later `HealthProfile` module supports reporting a profile instead of one number.
- **The concentration bounds and the "evolutionary attractor" theorem** (`thm:evoFormal` in Appendix 31). The report did not verify these, and they should not be used as established premises.

## What this does not affect

The current Lean modules, including those in the core (`formalization/ebe-core/EbECore.lean`), are separate and checked by CI. The broad necessity claims in these appendices (for example, that distributed, heterogeneous monitoring is "structurally necessary") go beyond what a sufficiency argument can show, and are not imported into the current results.
